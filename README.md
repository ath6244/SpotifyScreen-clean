# spotify-display

A Spotify now-playing display for a Samsung Galaxy Ace Duos (GT-S6802),
Android 2.3.6, 320×480. The laptop does everything; the phone is a dumb
terminal on the other end of the Wi-Fi.

This branch replaces the original Inky Impression e-ink project. Almost
nothing survived the change of output device — see the git history on `main`
for what was there.

## Setup

```powershell
pip install -r requirements.txt
copy config\.env.example .env      # then fill in client id + secret
set PYTHONPATH=src
python -m spotify_display.server
```

`.env` is read by the server directly, so there is no `source` step and no
`python-dotenv` dependency. Real environment variables override the file.

First run opens a browser **on the laptop** for the Spotify OAuth consent.
The token is cached in `var\spotify-token`; the phone never touches the auth
flow. Authentication completes before the listening port opens, so the phone
can never reach a half-started server.

## Requirements that are not code

- **The app owner needs Spotify Premium.** Development Mode apps require it
  as of the February 2026 API changes, and a lapsed subscription surfaces as
  an opaque auth failure — `GET /me` no longer returns the `product` field,
  so nothing can check it for you.
- **Redirect URI must be `http://127.0.0.1:8888/callback`, exactly.**
  Spotify rejects `localhost` and reports it as a redirect-uri mismatch
  rather than naming the real problem.

## Where this deviates from a normal web app

Four things do not survive contact with Android 2.3.

**WebSockets → HTTP long polling.** The Gingerbread stock browser has no
`WebSocket` constructor and no `EventSource`. `/api/state?v=N` blocks
server-side until the state version exceeds `N`, then returns immediately;
the client re-polls at once. Latency is equivalent, and the whole mechanism
is ~40 lines in `state.py`.

**Album art must be proxied.** The phone cannot complete a TLS handshake with
`i.scdn.co` — its stack predates SNI and modern ciphers. `art.py` downloads on
the laptop, resizes to 300px, and re-serves it over plain HTTP on the LAN.
Content-hashed filenames mean the device cache actually works.

**Glassmorphism is impossible in CSS here.** No `filter`, no
`backdrop-filter`. So the blur is a 96px pre-blurred JPEG generated by Pillow
and upscaled by the browser — about 3 KB.

**No SVG.** SVG support arrived in Android 3.0. The playback indicator is the
word "Playing", because a CSS-drawn triangle at this size has visible
stair-stepping on the device.

## Getting a fullscreen, always-on display

The stock browser cannot go fullscreen, and its URL bar eats roughly 50–60px
of a 480px-tall layout — enough to hide the progress bar. Options, best first:

1. **Opera Mobile 12.1** — last version supporting 2.3, Presto engine, far
   better CSS support than stock, and a real fullscreen mode.
2. A kiosk/fullscreen browser APK targeting API 10.
3. A 30-line WebView wrapper built against API 10 with an old SDK.

Then: Settings → Applications → Development → **Stay awake** (keeps the
screen on while charging), and set screen timeout to maximum. Keep brightness
low — this panel is not AMOLED, so the amoled theme saves no power, only
glare.

## Theming

Themes are pure CSS. `/?theme=cyberpunk` loads `static/themes/cyberpunk.css`.

`app.js` writes three album-derived values as inline styles: the accent color
onto `#fill` and `#badge`, and the blurred backdrop onto `#backdrop`. A theme
that wants a fixed palette overrides them with `!important` — see
`cyberpunk.css`. Adding a theme means adding one file. The backend has no
concept of themes, and neither does `app.js` beyond reading the query string.

## Adding a non-Spotify widget

`state.py` publishes a flat dict. Anything that produces the same keys
(`status`, `title`, `artist`, `progress_ms`, `duration_ms`, `art`) renders
without frontend changes. For genuinely different widgets, add a key to the
payload and a block to `index.html` — the long-poll transport and the version
counter are source-agnostic already.

## Things worth knowing before you tune it

- **A track change publishes three times.** Metadata goes out immediately
  with `art: null`, then art follows, then lyrics. Both slow fetches run on a
  worker thread so neither can delay the phone showing the new title. Stale
  workers are dropped if you skip again mid-fetch.
- **The progress bar is interpolated client-side.** The server only publishes
  when something unpredictable happens: track change, play/pause, or a seek
  more than 1.5s off the expected position. Pushing a frame per second would
  be ~30× the traffic for zero visible difference.
- **Poll interval is 3s.** Spotify rate-limits per app over a rolling 30s
  window; 3s is comfortable for one client. Do not drop below 1s.
- **`threaded=True` is load-bearing.** Each long poll parks a worker for up
  to 25 seconds. The default single-threaded Flask server would deadlock on
  the first request.
- **Flask's dev server is fine here** — one client on a home Wi-Fi network.
  If you ever expose this beyond the LAN, put it behind something real.
